# tdd-agent-teams

작업 단위는 **plan-task**(`plan/NNN-slug/task.md`)로, 구현은 이 스킬의 **TDD 팀**으로 진행한다.
이 세션이 **리드**가 되어 팀을 지휘하고, 각 팀은 `.claude/agents/`의 서브에이전트로 스폰한다.
모든 팀은 `karpathy-guidelines` 스킬을 미리 불러온 상태로 시작한다(에이전트 정의의 `skills:`). 리드도 같은 원칙을 따른다.

| 팀 | 에이전트 | 하는 일 | 건드리면 안 되는 것 |
|---|---|---|---|
| Red | `tdd-red` | 완료 기준 → 실패하는 테스트 | 프로덕션 로직 |
| Green | `tdd-green` | 테스트를 통과시키는 최소 코드 | 테스트 |
| Refactor | `tdd-refactor` | 동작 유지한 채 단순화 + 리뷰 | 동작, 무관한 코드 |

## 0. 준비 (리드)
1. 대상 계획 폴더를 정한다. 사용자가 지정하지 않았으면 `plan/` 아래 진행 중인 계획을 보여주고 고르게 한다.
2. `plan.md`와 `task.md`를 읽고 **이번 사이클에서 할 작업 하나**를 고른다. 순서대로 첫 번째 `[ ]` 항목이 기본이다.
3. karpathy 원칙 1·4에 따라 작업을 **검증 가능한 완료 기준**으로 바꾼다. 예: "상품 목록 조회" → "GET /api/products?category=book → 200, book 카테고리 상품만 반환", "없는 카테고리 → 빈 목록". 해석이 여러 개거나 설계가 비어 있으면 **팀을 스폰하기 전에** 사용자에게 묻는다.
4. DB 테스트는 Testcontainers를 쓰므로 Docker가 켜져 있는지(`docker info`) 확인한다. 로컬 MySQL(compose)은 테스트에 필요 없다.
5. `task.md`에서 해당 항목을 `[~]`로 바꾼다.

## 1. Red 팀
`Agent(subagent_type: "tdd-red")`로 스폰한다. 프롬프트에 담을 것: 계획 폴더 경로, 작업 원문, 완료 기준 목록, 관련 파일 경로.

**리드 검증:** 보고서만 믿지 말고 리드가 직접 대상 테스트를 실행해 **실패하는지**, 실패 이유가 컴파일·설정 오류가 아닌지, 완료 기준이 빠짐없이 테스트로 옮겨졌는지 확인한다. 문제가 있으면 구체적인 지적을 담아 Red를 다시 스폰한다.

## 2. Green 팀
`Agent(subagent_type: "tdd-green")`로 스폰한다. 프롬프트에 Red 결과 보고서를 그대로 넣는다.

**리드 검증:** `./gradlew test`를 직접 실행해 전체가 통과하는지 확인하고, `git diff`(저장소가 없으면 변경 파일 목록)로 테스트 파일이 바뀌지 않았는지 확인한다.
- 실패하면 실패 출력을 담아 Green을 다시 스폰한다. **같은 작업에서 Green이 3번 실패하면** 멈추고 사용자에게 상황을 보고한다.
- Green이 "테스트가 틀렸다"고 보고하면 리드가 판단한다. 맞으면 Red를 다시 스폰해 테스트를 고치고, 아니면 이유를 붙여 Green을 다시 스폰한다.

## 3. Refactor 팀
`Agent(subagent_type: "tdd-refactor")`로 스폰한다. 프롬프트에 Red·Green 보고서와 이번 사이클의 변경 파일 목록을 넣는다.

**리드 검증:** `./gradlew check`를 실행해 테스트·Spotless·Checkstyle이 전부 통과하는지 확인한다. 실패하면 Refactor의 변경을 되돌리거나 다시 스폰해 고친다.

## 4. 마무리 (리드)
1. `task.md`에서 항목을 `[x]`로 바꾸고 바로 아래에 메모를 남긴다.
   `> 메모: <날짜> 테스트 <클래스명> 추가, 전체 <n>/<n> 통과`
2. Green이 보고한 설계 결정은 `plan.md` 결정 기록에 추가한다.
3. Refactor의 리뷰 지적 중 후속 작업이 필요한 것은 `task.md`에 `[ ]`로 추가하고 사용자에게 알린다.
4. 패키지·엔티티·API·외부 연동·설정 중 바뀐 게 있으면 루트의 `ARCHITECTURE.md`에서 해당 절을 현재 상태로 고친다(규칙: `AGENTS.md` 2절). 바뀐 게 없으면 건너뛴다.
5. **커밋·push**: 이번 사이클의 변경(코드·테스트·`task.md`·`plan.md`·`ARCHITECTURE.md`)을 한 커밋으로 남긴다. 제목은 Conventional Commits(CONVENTIONS.md 8절)로 작업 내용을 쓴다(예: `feat: 주문 취소 도메인 규칙 추가`). 브랜치가 `main`이면 커밋하지 말고 멈춰 사용자에게 알린다(계획 브랜치는 `plan-task new`가 만든다). 브랜치에 upstream이 있으면 `git push`해서 Draft PR과 CI에 반영한다.
6. 사용자에게 사이클 결과를 짧게 보고한다: 작업, 추가한 테스트, 변경 파일, 전체 테스트 결과, ARCHITECTURE.md 갱신 여부, 커밋·push 여부, 남은 지적.
7. 이번 사이클로 `task.md`의 `[ ]`·`[~]`가 모두 없어졌으면 **최종 검증**(`AGENTS.md` 1절 ⑤)을 한다: `./gradlew check`를 실행하고(`spotlessApply`는 붙이지 않는다), `ArchitectureTest` 결과 XML로 ArchUnit이 실제로 돌았는지 확인한 뒤 `task.md` 맨 아래에 결과를 남긴다. 통과하면 `/plan-task archive NNN`을 제안하고, 실패하면 고칠 일을 `[ ]`로 추가해 보고한다.
8. 사용자가 "계속"을 요청했으면 다음 `[ ]` 항목으로 0단계부터 반복한다. 요청이 없으면 한 사이클만 하고 멈춘다.

## 운영 규칙
- **한 번에 한 사이클, 한 작업.** 팀은 같은 파일을 만지므로 Red·Green·Refactor는 반드시 순서대로 스폰한다.
- 서로 다른 계획의 독립된 작업을 동시에 진행할 때만 `isolation: "worktree"`로 팀을 병렬 실행할 수 있다(git 저장소 필요). 병렬로 돌렸다면 마지막에 리드가 결과를 합치고 전체 테스트를 다시 실행한다.
- 서브에이전트는 다시 서브에이전트를 스폰할 수 없다. 팀 사이의 정보 전달은 반드시 리드를 거친다.
- 사이클이 사소한 작업(오타, 설정값 하나 변경 등)이면 팀을 스폰하지 말고 리드가 직접 처리하고 사용자에게 그렇게 했다고 알린다.
